> **보고서 요약:** 한국연구재단 연구비 규정 Q&A를 위해 GPT-4o와 Upstage Solar 임베딩 기반 RAG 챗봇을 구축, 조문·의미청크 분할과 영어번역 후 BM25를 결합한 하이브리드 검색으로 조문 검색 성공률 90% 이상을 달성함.

# 1. 서론 <!-- id: 2024-08_c1 -->

> **요약:** 연구자 문의 응대에 많은 시간이 소요되는 문제를 해결하기 위해 한국연구재단은 내부 법규와 FAQ를 활용한 RAG(검색증강생성) 기반 Q&A 챗봇을 개발했으며, 조문·의미적 청크·BM25 조합의 검색 방식과 GPT-4o-mini 모델을 통해 저비용으로 80% 이상의 조문 검색 성공률을 달성했고, 이후 장에서 시스템 구현, 데이터 처리, 매칭 실험, 하이브리드 검색기 적용 및 향후 연구 방향을 순서대로 다룬다.

한국연구재단의 주요 업무 중 하나는 연구자들에게 과제 정보와 연구비 사용 규정을 신속하고 정확하게제공하는 것이다. 재단은 이를 위해 관련 법규와 게시판을 통해 다양한 정보를 제공하고 있지만, 정보의양이 방대하고 구조가 복잡하여 연구자들이 이를 완전히 숙지하고 활용하는 데 어려움을 겪고 있다. 이러한 어려움으로 인해 연구자들은 빈번하게 재단에 문의하게 되며, 재단 직원들은 질의 응답에 많은 시간을 소비하게 된다. 때로는 답변을 제공하는 데 하루 이상이 소요되기도 한다. 본 연구는 이러한 문제를 해결하고자 최근 개발된 생성형 인공지능(AI)을 활용하는 것을 목표로 하였다.

생성형 AI는 신속하고 정확한 답변을 제공하여 재단의 인력 소모를 줄일 수 있는 잠재력이 있다. 그러나 방대한 법규와 복잡한 질문 특성으로 인해 AI가 관련 법규를 정확히 찾지 못하거나 환각(hallucination) 현상이 발생할 수 있다. 특히 재단의 데이터는 ChatGPT등의 생성형 언어모델의 훈련에사용되지 않았기 때문에 다른 법규의 답을 대답하는 등의 문제를 일으킬 가능성이 크다. 또한 다수의연구자에게 서비스를 제공할 경우 비용도 중요한 문제로 대두된다.  이러한 배경에서, 본 연구는 내부정보를 활용하는 RAG(Retrieval-Augmented Generation) 기반의 Q&A 시스템을 개발하였다 [1 - 3].

가장 단순한 RAG 구현 예로는 OpenAI의 GPT 모델을 이용하는 방식을 들 수 있다 [4]. GPTs를 이용할 경우 연구재단의 문서를 업로드하고, 그 문서를 기반으로 질문에 답하도록 하는 것이다. 그러나 이방법은 몇 가지 문제를 가지고 있다. 첫째, OpenAI의 GPT 모델을 사용하려면 유료 계정이 필요하다.유료계정이 있어야 개발이 가능하며, 단순 이용의 경우에는 무료계정도 가능하지만 하루 사용량이 몇개로 제한이 되어 있다.  또한 검색할 때마다 많은 토큰을 사용하게 되어 시스템 허용량을 초과할 수있다. 셋째, 종종 부정확한 답변이 생성되기도 하며 이를 고칠 방법이 마땅치 않다. 이러한 문제로 인해사용 편의성과 시스템 신뢰성이 떨어지는 결과를 낳을 수 있다.

본 연구에서는 이러한 문제를 해결하기 위해 법규를 미리 쪼개어(chunk) 임베딩 벡터로 저장하고, 질문이 들어오면 임베딩 벡터 간의 매칭을 통해 가장 가까운 조항(rule)을 찾는 방식을 채택했다. 문서를 임베딩 벡터로 변환하는 작업은 시스템 구축 시 한 번만 필요하며, 이후에는 질문을 임베딩 벡터로 변환해 매칭하는 방식이다. 코사인 유사도(cosine similarity)를 이용해 매칭된 조항을 GPT-4o-mini 모델에 제공하고, 질문에 대한 답변을 생성하도록 했다. 관련성 있는 조항을 제공함으로써 환각의 위험을 크게 줄일 수 있었다. 이 시스템은 Streamlit 기반으로 개발되어, 누구나 PC나 휴대폰에서 쉽게 접근할 수있도록 설계되었다 [5].

본 개발된 시스템에서 중요한 부분은 관련 조항을 정확히 찾아내는 방법이다. 단순히 조항(rule)을 일정한 글자 수로 나누는 것만으로는 정확도가 떨어지기 때문에, 다양한 방법을 실험한 후 가장 적합한 방식을 채택했다. 본 방법은 조문, 의미적 청크(semantic chunk, 의미 단위로 나눈 부분), BM25 알고리즘등을 조합하여 검색의 정확도를 높였다.

또한 기존의 전화 상담을 통해 수집된 FAQ(Frequently Asked Questions)를 활용하여 질문과 유사한 FAQ 사례 두세 개를 찾아 생성형 AI에 제공함으로써 보다 정확한 답변을 생성할 수 있도록 했다. FAQ는 쉽게 추가할 수 있기 때문에, 시스템이 사용될수록 정확도가 점차 향상된다. 새로 얻은 FAQ를 쉽게추가할 수 있는 소프트웨어도 본 연구의 일환으로 제공되었다.

운영 비용도 중요한 고려사항이었다. 본 시스템은 사용자가 필요로 하는 규정이나 조항을 신속하게 찾을 수 있도록 지원하며, 자주 묻는 질문에 대한 답변을 미리 준비해두는 구조를 가지고 있어 효율적이다. 이로 인해, GPU가 없는 서버에서도 대량의 질의를 실시간으로 처리할 수 있도록 최적화되었다. OpenAI GPT-4o-mini 모델을 사용할 경우, 질의 한 번당 약 200원 내외의 비용이 소요되어 매우 저렴하다 [4].

본 시스템이 참조하는 데이터는 "연구개발비 사용기준", "연구관리혁신법 법률", "연구관리혁신법 시행령" 등의 문서로, 긴 조항은 여러 부분으로 나누어 총 261개의 조항을 포함하고 있다. 또한, 기존에 수집된 전화 상담 내용 기반의 약 800개의 FAQ도 포함되어 있다. 데이터베이스는 쉽게 업데이트 및 확장할수 있는 구조로 설계되었으며, 실제 현업에서 나온 매우 까다로운 질문들을 평가 세트로 사용해 80%이상의 조문 찾기 성공률을 달성했다. GPT-4o 모델을 통해 답변을 생성함으로써 사용자가 필요한 정보를 보다 명확하게 제공할 수 있었다.

본 보고서는 이 연구와 시스템 개발의 전 과정을 설명하고 있다. 제2장에서는 개발된 소프트웨어의 사용자 인터페이스와 간단한 사용법, 그리고 몇 가지 테스트 사례를 소개하고, 제3장에서는 데이터 처리방법을 설명한다. 여기에는 PDF 파일을 CSV 형태로 변환하고, 조항을 의미 단위로 쪼개는 방법(semantic chunking), 키워드 생성, FAQ 파일 변환 및 임베딩 벡터 추가 과정이 포함된다. 제4장에서는질의와 조문 매칭 실험에 대해 다루고, 평가에 사용된 데이터셋, 임베딩 모델(OpenAI, Solar 등)과 리랭킹(reranking) 효과를 분석한다 [6]. 정확도를 높이기 위한 여러 기법들, 예를 들어 BM25, 키워드 유사도 보너스, 카테고리 필터링 등에 대해서도 설명한다. 제5장에서는 널리 쓰이는 RAG 프레임워크인 LlamIndex를 사용한 하이브리드 검색기(hybrid retriever)와 GPT 모델을 이용한 구현 방식을 다루고,마지막 제6장에서는 결론 및 향후 연구 방향을 제시하며, 국내 언어모델이나 자체 언어모델을 활용할가능성에 대해 논의한다 [7].

본 보고서가 연구재단의 연구비 사용 규정 질의-응답 시스템 개발의 중요성과 가치를 잘 전달하여 개발된 시스템이 널리 활용되기를 기대한다.

# 2. 개발된 SW의 사용법 <!-- id: 2024-08_c2 -->

> **요약:** Streamlit 기반으로 개발된 시스템은 웹 브라우저에서 링크 접속만으로 실행되며, 사이드바에서 이름·소속기관 유형을 입력한 뒤 질의를 입력하면 AI Summary와 근거 Rule/FAQ를 확인하고 피드백을 제출할 수 있는 사용법을 설명하고, 40개 질문 기반 성능 평가에서 Hybrid 검색(청크 유사도+영어 번역 후 BM25) 버전이 RERANK 및 GPTs 버전보다 요약·근거 정확도와 히트율(75% vs 40%) 모두에서 우수함을 확인하였다.

본 시스템은 Streamlit 기반으로 개발되었으며, 사용자는 웹 브라우저(web browser)를 통해 쉽게 접근할 수 있다. 시스템 링크를 개인 PC의 웹 브라우저에 복사하면 즉시 실행이 가능하다. 이 장에서는 SW사용법(2.1)과 테스트 결과(2.2)에 대해 설명한다.

## 2.1. 사용법 <!-- id: 2024-08_c2s1 -->

본 프로그램의 링크를 웹 브라우저에 입력하면 화면이 나타나며, 사이드바에 이름이나 ID를 입력하는창이 뜬다. 이 입력은 피드백 기록에 사용되며, 필수 사항은 아니다. 향후 시스템 오용 방지를 위한 장치도 추가될 수 있다. 소속기관의 형태를 선택하는 옵션이 제공되며, '대학(산학협력단 포함)', '정부출연기관', '기타 비영리기관(대학, 정부출연기관 제외)', '영리기관(기업, 공기업)' 중 하나를 선택해야 한다.이는 특정 조항이 특정 기관 형태에만 적용될 수 있기 때문이다. 시스템 내부에서는 기관의 종류와 관계없이 적용되는 규정을 '공통'으로 분류해 제공한다.

그림 2.1 사용자 화면

사이드바에는 사용법 설명도 제공되며 오른쪽 메인 화면에서는 질문 입력 창이 있으며, 사이드바를 접으면 메인 화면을 더 넓게 사용할 수 있다. 사이드바에서는 이름 또는 id를 입력할 수 있는데, 이는 log file에 기록이 된다.  이름 또는 id를 남기지 않더라도 익명으로 사용할 수 있다.  그리고 소속기관의 형태를 선택하여야 한다.  그리고 간단한 사용법이 나온다.  먼저 Query(질의)를 입력하고, AI_Summary버튼을 누르고, 이를 확인 후 근거가 되는 Rule 또는 FAQ를 볼 수 있다.  이 때 AI_Summary과정에서해당하는 규정의 숫자를 줄이는 RERANK 과정도 함께 수행되므로 근거가 되는 Rule 또는 FAQ의 개수는 대개 2개 이내로 줄어서 보는데 편리하다.

메인 화면에서는 주의하여야 할 점 두가지를 알려준다. 하나는 연월을 직접 넣는 경우로서 조문이나 FAQ 검색에 어려움이 있다.  그리고 생성형 AI의 환각의 위험을 경고한다.

창에 질문을 입력하면 SW가 응답을 한다.  예를 들어 "박사과정 인건비 기준은 얼마인가요?"라는 질문을 입력하면, 다음의 화면이 나온다.

# 3. 데이터 전처리 방법 <!-- id: 2024-08_c3 -->

## 3.1. 개요 <!-- id: 2024-08_c3s1 -->

> **요약:** 연구비 관리 규정 등 PDF 자료는 텍스트 추출이 용이하나 수식 등 이미지는 별도 처리가 필요하며, 단순 글자 수 기준 분할 대신 md 변환 후 조문 단위 CSV 저장, 의미 단위 분할(semantic chunking) 및 키워드 생성 과정과 FAQ 데이터의 CSV 변환 및 임베딩 벡터 추가 과정을 설명한다.

연구비 관리 규정 등의 자료는 대부분 PDF 형식으로 제공되며, PDF 문서에서 텍스트는 쉽게 추출할수 있다. 다만, 일부 문서내에 섞여있는 수식 등 일부 이미지는 개별 처리해야 한다. LangChain이나 LlamaIndex와 같은 RAG(Retrieval Augmented Generation) 소프트웨어들은 대개 이 텍스트를 일정 길이로 나누어 임베딩 벡터로 변환하지만, 단순히 글자 수 기준으로 나누다 보면 의미가 왜곡되어 성능저하가 발생할 수 있다.

본 장에서는 PDF 문서를 md(metadata) 형식으로 변환한 후, 조문 또는 조항(rule)을 CSV 파일 형식으로 저장하고, 이를 의미 단위로 나누는 방법(semantic chunking)과 각 조항의 키워드를 생성하는 과정을 설명한다. 또한, FAQ 데이터를 Excel에서 CSV로 변환하고 임베딩 벡터를 추가하는 과정도 다룬다.

## 3.2. 데이터 변환 과정 <!-- id: 2024-08_c3s2 -->

> **요약:** 연구비 관리 규정 PDF 문서를 구조를 유지한 Markdown 파일로 변환한 뒤 의미 단위로 조항을 분할하는 semantic chunking을 거쳐 CSV 파일로 변환하였으며, GPT-4o를 활용해 각 조항의 요약과 질문을 생성하고 엑셀에서 항목·키워드 등 추가 정보를 입력하여 최종 CSV 파일을 완성하였다.

1. PDF에서 Markdown 파일 변환

Markdown(MD) 파일은 경량 마크업 언어로, 텍스트 문서를 간단한 문법으로 서식화할 수 있다. 조항등을 나타날 때 줄바꿈 등이 있는 법령 등은 ChatGPT를 이용하여 쉽게 Markdown 파일로 변환할 수있다.  Markdown 파일은 주로 .md또는 .markdown확장자를 사용하며, 일반 텍스트 기반으로 간단한 메모장에서도 열 수 있다. 주요 기능은 다음과 같다:

- 제목 및 서브제목: #, ##, ###로 표시

- 목록: -, *, +로 생성

- 강조: 별표(*)나 밑줄(_)로 굵게(bold) 또는 기울임(italic) 표시

- 코드 블록: ```로 감싸서 코드 형식을 유지

2. Markdown에서 CSV 파일 변환

CSV(Comma-Separated Values) 파일은 데이터를 쉽게 교환하고 분석하기 위해 자주 사용된다. CSV파일은 각 행이 데이터 레코드를 나타내며, 쉼표로 각 속성을 구분한다. Python의 Pandas 라이브러리를사용하면 CSV 파일을 DataFrame으로 변환하여 편리하게 처리할 수 있다.

연구비 관리 규정의 PDF 문서를 우선 MD 파일로 변환한 후 CSV 파일로 변환하는 과정이 필요하다.어떤 조문은 2페이지가 넘어가고 너무 길기 때문에, 일부 조문은 제2조-1, 제2조-2와 같이 우선 사람이 보면서 나누었다.  이러한 조문의 개수는 많지 않다.  그리고 이렇게 나누었어도 하나의 조문은 일반적으로 길기 때문에, 의미 단위로 쪼개지 않으면 검색 성능이 떨어진다. 본 연구에서는 문서의 구조를유지하면서 MD 파일로 저장한 후, 이를 CSV 파일로 변환하였다. 이때, 각 조항을 의미 단위로 쪼개는작업, 즉 semantic chunking 을 수행하였다. 또한 각 조항에 대한 요약(summary)과 각 조항을 기반으로 하는 질문(question) 생성도 수행한다.  이 요약과 질문 생성은 GPT-4o를 이용하여 수행하였다. 아래는 전체 플로우(flow)를 보인다.

> **요약:** 조문이 길어지면 질의 매칭이 어려워지므로 일정 길이 분할 대신 GPT-4o를 활용해 의미 단위로 분할(semantic chunking)하고 요약을 생성하며, 그 결과는 row_id, doc_name, semantic_chunk, chunk_num, statistics, chunk_success, summary, quest_list 등의 열을 포함한 CSV 파일로 저장되고 글자 수 차이가 20 이상이면 chunk_success가 False로 표시되어 사람이 수정하도록 한다.

각 조문이 길어질 경우, 질의와 매칭하기 어려워지므로 의미 단위로 쪼개는 작업이 필요하다. 일정한 글자 길이로 나누는 것보다, 의미 단위로 나누는 방식이 성능 향상에 효과적이다. 현재 긴 텍스트를 의미단위로 쪼개는 방법들이 몇 개 있고 대부분 임베딩벡터(embedding vector)를 사용하는데, 실험을 한 결과 성능이 좋지 않았다. 이를 위해 여러 방법이 존재하지만, 본 연구에서는 OpenAI의 GPT-4o 모델을활용한 의미 단위 분할을 적용하였다.  앞의 그림 3.1에 보이는 것과 같이 quest_kwd_gen_new.py 프로그램을 이용하여 이 과정을 수행한다.

## 3.6. FAQ 파일 추가 또는 생성방법 <!-- id: 2024-08_c3s6 -->

> **요약:** 전화 상담 기반 FAQ 약 800개를 관리하는 시스템에서, 부록의 faq_embedding_update.py를 이용해 신규 FAQ(Excel 형식, category·keywords·question·answer 항목)를 CSV로 변환하여 기존 데이터와 결합·키워드 생성·임베딩 벡터 업데이트를 처리하는 방법과 실행 과정을 설명한다. 이 프로그램은 GPT-4o로 키워드를 생성하고 Upstage Solar 임베딩으로 벡터를 변환하며, 신규 데이터만 추가 처리할 수 있어 효율적이나 기존 데이터 삭제 시에는 전체 재생성(약 1~2시간)이 필요하다.

FAQ(Frequently Asked Questions) 데이터는 연구재단의 전화 상담을 통해 수집된 복잡한 상황에 대한명확한 답변을 제공한다. 현재 시스템에는 약 800개의 FAQ가 포함되어 있으며, 새로 추가된 FAQ 데이터를 시스템에 반영하는 것은 쉽다. 부록에 제공된 ’faq_embedding_update.py‘ 파일을 이용하면, 새로추가된 데이터를 간편하게 처리할 수 있다.

추가할 FAQ 파일은 Excel 형식으로 준비하며, category, keywords, question, answer의 네 개 항목을포함해야 한다. 여기에서 category column은 적용되는 대상의 그룹으로서 [공통, 출연(연), 영리기관,기타 비영리기관, 대학] 중의 하나를 넣으면 된다.  공통은 모두에게 적용되는 것으로서 애매할 때는 공통을 넣으면 된다.  keywords 컬럼은 현재 큰 의미가 없다.  왜냐하면 이 faq_embedding_update.py 에서 keywords를 새로 생성하기 때문이다.

추가 FAQ는 CSV 파일로 변환한 후 프로그램에 반영된다. 기존 데이터를 업데이트할 때 전체 키워드를새로 생성할 필요 없이, 새로 추가된 데이터만 처리할 수 있다.  이 프로그램의 장점은 소량의 FAQ data가 얻어졌을 때 시간이 걸리는 전체의 keyword를 다시 생성하던가 embedding vector를 만들 필요가 없이, 바뀐 것만 새로 추가할 수 있는 것이다.  그런데 기존의 것에서 일부를 빼려고 하면 전체 keyword 생성과 embedding vector 생성을 처음부터 다시 해야 한다.  이 경우 약 한시간내지 두시간정도의 시간이 걸린다.

사용자가 입력한 질의(query)에 대해 예산 항목, 활동비, 관리 항목과 관련된 키워드를 찾아주는기능을 수행한다. 이를 위해 질의를 기반으로 GPT-4o를 사용해 생성한 프롬프트를 전송하고,GPT가 반환하는 답변에서 키워드를 추출한다.

3. FAQ 파일 처리 (process_faq_file)

새로운 FAQ 파일을 읽어 각 질문에 대한 키워드를 생성하고, 데이터를 DataFrame에 저장한다.각 질문과 답변의 내용을 결합해 get_related_keyword() 함수를 통해 키워드를 생성한 후, 이를 CSV 파일에 기록한다.

4. 임베딩 업데이트 (update_embeddings)

FAQ 데이터의 질문을 Solar 모델을 통해 임베딩 벡터로 변환하고, 기존 임베딩 파일이 있을 경우 이를 업데이트한다. 새로 추가된 질문에 대한 임베딩을 기존 임베딩과 결합하여 업데이트된임베딩 파일을 저장한다.

5. 메인 함수 (main)

프로그램의 메인 로직으로, 기존의 FAQ 데이터를 불러오고, 새로운 FAQ 파일을 처리하여 데이터를 업데이트한 후, 새로운 임베딩 벡터를 생성하여 저장한다. 사용자는 프로그램 실행 중에 기존 CSV 파일과 임베딩 파일을 지정하고, 새로운 FAQ 파일을 처리할 수 있다.이 프로그램은 질의에 대한 키워드를 자동으로 생성하고, 데이터를 최신화하는 기능을 통해 FAQ시스템의 성능을 개선할 수 있도록 설계되었다.

## 4.1. 개요 <!-- id: 2024-08_c4s1 -->

> **요약:** RAG 시스템은 문서를 법 조항 단위 및 의미론적 청크로 전처리해 임베딩 벡터로 저장하는 구축 과정과 사용자 질의를 임베딩해 벡터 DB에서 유사 조항·청크를 Top_K개 검색하는 사용 과정으로 구성되며, 히트율은 문서 분할 방식과 임베딩 모델, Top_K 값에 따라 달라지므로 본 연구에서는 이들 요소의 영향을 실험하였다.

RAG(Retrieval Augmented Generation) 시스템에서 가장 중요한 것은 검색 성능을 향상시키는 것이다. RAG 시스템은 두 단계로 구성되며, 먼저 구축 과정과 사용 과정으로 나눌 수 있다.

먼저 RAG 시스템을 구축하는 과정을 아래의 그림을 이용하여 설명한다.  제일 먼저 (ㄱ)에 해당하는부분에서 연구비관리에 관한 문서를 올리면, (ㄴ)에서 제 3장에서 설명한 전처리가 이루어진다.  문서를단순히 일정 길이로 나누지 않고, 법 조항 단위로 나눈 후에 하나의 조항도 여러개의 조각(chunk)로 나누었다.  이 때 의미론적 나누기(semantic chunking)방법을 개발하였다. 이렇게 나누어진 조항(rule)과각 chunk 들은 임베딩 언어모델(embedding language model)에 의해서 임베딩 벡터로 바뀌고, 이것이벡터 DB에 저장이 된다.

RAG시스템을 사용자가 사용하는 과정을 설명한다. 아래 그림의 (ㄹ)부분에서 사용자가 질의(query)를입력하면, 이 질의는 (ㄷ)부분에서 동일한 임베딩 언어모델에 의해서 임베딩 벡터로 바뀌고, 이 질의의임베딩 벡터를 이용하여 벡터 DB에 미리 저장된 문서의 임베딩 벡터와 코사인 유사도 측정 등을 통한방법으로 가장 가까운 조항 또는 청크(chunk)를 찾는다.  이 때 보통 가장 유사한 것 하나만을 찾지 않고, Top_K 개를 찾는다.  이 때 Top_K개에 맞는 조항이나 청크(chunk)가 있을 확률을 히트율(hit rate)라 하며, 당연 100%를 목표로 하지만 많은 경우 그렇지 못하다.  당연 Top_K의 개수가 크면 히트율이 높아지지만, 나중에 생성형 AI가 답변을 생성할 때 더 많은 자료를 보아야 하기 때문에 필요한 토큰의 숫자가 증가하고 이는 비용 상승을 의미한다.  히트율은 그리고 문서를 쪼개는 방법(Rule 또는 chunk)에 따라 크게 달라지며, 또한 임베딩 모델의 종류에 따라 다르게 나온다.  본 연구에서는 문서나누기 방법, 임베딩 모델, 그리고 Top_K 값의 영향을 실험하였다.

## 4.4. 생성형 AI 기반 ReRANK 방법의 성능평가 <!-- id: 2024-08_c4s4 -->

> **요약:** Top_K 값이 커질수록 히트율은 높아지지만 후보 규정 수가 과다해지는 문제를 GPT-4o 기반 Re_Rank로 보완하여, Top_K 4·6·8 조건에서 각각 성공률 24/40, 30/40, 29/40을 얻었으며 Top_K 6이 최적 조건으로 나타났다.

## 5.1. 개요 <!-- id: 2024-08_c5s1 -->

이번에 개발된 프로그램은 Streamlit기반으로 구현되었으며, 웹 브라우저에서 쉽게 실행할 수 있도록 설계되었다. 사용자는 프로그램의 링크만 있으면 웹 브라우저를 통해 즉시 접속해 실행할 수 있다. 그런데 Streamlit의 기본 특성상 프로그램에 입력이 들어오면 전체 프로그램이 전부 재실행되는 문제가 있다.이로 인해 화면에 있던 내용이 사라질 수 있는데, 이를 방지하기 위해 streamlit.state변수를 사용하여데이터를 저장하고, 필요 시 이를 다시 불러와 화면을 복구하도록 하였다.

## 6.1. 결론 <!-- id: 2024-08_c7s1 -->

> **요약:** 한국연구재단 연구비 사용 규정 질의응답을 위해 GPT-4o 기반 RAG 시스템을 구축하고 의미 단위 조항 분할, 키워드 매칭, 영어 번역 후 BM25 적용 등을 결합한 하이브리드 검색 방식을 실험한 결과, 조문 찾기 성공률 90% 이상과 낮은 오류 답변율을 달성하여 기존 대비 부정확한 답변과 환각 문제를 크게 개선하였다.

본 연구는 한국연구재단의 연구비 사용 규정에 대한 질의 응답 시스템을 개선하기 위해 생성형 AI와 RAG(Retrieval-Augmented Generation) 기술을 활용한 시스템을 개발하였다.

본 시스템은 OpenAI의 GPT-4o 모델을 기반으로 하며, 문서 청크(Chunk)를 임베딩 벡터로 변환하고코사인 유사도를 활용하여 관련성이 높은 규정을 검색하는 방식으로 구현되었다. 이를 통해 기존에 발생하던 부정확한 답변 및 환각(hallucination) 문제를 크게 줄일 수 있었고, 연구비 사용 규정에 맞는 정확한 답변을 제공할 수 있었다. 또한, 연구재단의 자주 묻는 질문(FAQ)을 기반으로 시스템이 더 정확한답변을 제공할 수 있도록 설계되었다.

성능 개선을 위한 여러 실험이 진행되었다. 문서를 일정한 길이 또는 조항별로 나누는 기존 방식 대신,조항을 의미 단위로 분할하여 임베딩을 생성하는 방식이 성능 향상에 중요한 것을 확인하였다. 또한 조문 또는 FAQ에 미리 생성형 AI를 이용하여 키워드(keyword)를 생성하고, 질의(Query)가 들어오면 여기에서 같은 방식으로 키워드를 생성하고, 이 키워드 매칭을 이용하여 탐색의 정확도를 높였다. 종래의문서 검색 방식인 BM25 알고리즘의 경우 한글에서 좋은 성능을 보이지 못하였다.  그렇지만 한글 문서를 영어로 번역 후 적용시에 더 나은 성능을 보여 주었다.  특히 영어번역의 일관성을 유지하기 위하여 GPT-4o를 이용한 번역이 구글번역 API를 이용한 것보다 월등히 나은 성능을 보여주었다.  최종 시스템은 청크(chunk)기반의 유사도 매칭과 BM25 알고리즘을 결함한 혼합검색(Hybrid Retriever)을 이용하였다.. 최종적으로, 본 시스템은 90% 이상의 조문 찾기 성공률을 달성하였으며, 매우 낮은 오류 답변율을 보여서 연구재단의 규정 질의 응답 시스템에 실질적인 개선을 제공할 수 있음을 확인하였다.

## 6.2. 향후 연구 방향 <!-- id: 2024-08_c7s2 -->

> **요약:** 보안을 위한 내부 서버 기반 자체 모델 도입, 한국어 성능 개선 및 한영 동시 번역 검색 활용, FAQ·규정 업데이트 자동화, 생성형 AI 및 에이전트 기술 발전에 따른 기능 확장 등이 향후 과제로 제시되며, 이러한 개선을 통해 연구재단뿐 아니라 다양한 기관으로 시스템을 확대 적용할 수 있을 것으로 기대된다.

본 연구는 RAG 기반 시스템을 개발하고 그 성능을 개선했지만, 아래 정리한 것과 같이 다양한 성능 개선과 확장의 가능성이 있다.

첫째, 보안 문제로 인해 내부 서버에서 실행되는 모델의 필요성이 증가하고 있다. 현재 사용 중인 OpenAI의 GPT-4o 모델은 클라우드 기반 서비스로 운영되는데, 연구자들이 민감한 데이터를 다루는경우, 외부 서버에 의존하는 것이 적절하지 않을 수 있다. 이를 해결하기 위해 내부 서버에서 실행될 수있는 자체 모델이나 국내에서 개발된 언어 모델을 도입할 필요가 있다. 이를 통해 연구 데이터를 보호하면서도 필요 기능을 유지할 수 있을 것으로 기대한다.

둘째, 현재 사용 중인 대규모 언어 모델 중 일부는 한국어 성능이 아직 부족한 상황이다. 예를 들어,Llama 3.1과 같은 최신 공개 모델은 영어에서 뛰어난 성능을 보이지만, 한글 처리에서는 여전히 개선의여지가 많다. 이로 인해 한글 질의에 대한 정확도를 높이기 위한 추가 연구가 필요하다. 특히 한국어에최적화된 자체 언어 모델을 개발하거나, 국내에서 개발된 한국어 언어 모델을 적용해 검색 성능을 향상시키는 방안을 모색할 계획이다.  또한 앞서 실험한 바와 같이 한글-영어 동시 번역된 모델을 이용한검색 및 생성요약은 매우 기대되는 기술로 생각한다. 이 경우 서로 다른 언어로 기술된 자료를 이용함으로써 환각의 위험을 최소화시키고 또한 BM25 등 단어기반 검색을 활용하기 쉬운 장점이 있다.

셋째, 관련 규정 또는 FAQ 시스템의 지속적인 업데이트를 위한 자동화 방안의 개발을 제안할 수 있다.현재는 관리자가 새로운 FAQ를 수동으로 추가해야 하지만, 향후에는 웹사이트에 업로드된 FAQ가 자동으로 시스템에 반영되도록 시스템을 확장할 수 있다. 물론 자주 있는 일은 아니지만 관련 규정의 업데이트도 비슷한 방법으로 자동화할 수 있다.  이를 통해 연구자들이 최신 정보를 실시간으로 제공받을수 있으며, 관리자의 업무 부담도 줄어들 것으로 기대된다.

현재 국내의 다양한 기관에 비슷한 시스템이 필요하다.

일예로 범부처통합연구지원시스템 www.iris.or.kr)에는 Chatbot이 설치되어 있으나, 그 답변능력은 기대치 이하이다. 다양한 연구 기관에서 본 시스템을 폭넓게 활용할 수 있도록 추가적인 확장이 필요하다. 이와 같은 개선을 통해 본 시스템은 연구재단뿐만 아니라 다양한 기관에서 유용하게 사용될 수 있을 것으로 기대되며, 연구자들에게 실질적인 도움을 제공할 수 있는 중요한 도구로 자리매김할 수 있을 것이다.

넷째, 생성형 AI의 기능은 매우 빠르게 발전하고 있다. 생성형 AI의 경우 OpenAI뿐만 아니라 Claude 3.5, 그리고 Google의 제미나이 등이 경쟁하고 있으며, 이들 경쟁제품들은 OpenAI의 GPTs에 해당하는프로그램 없는 앱 제작 기능을 제공하고 있다. 본 프로그램 개발에서도 전통적 프로그래밍 대신에 생성형 AI를 이용한 의미적 청크 나누기(semantic chunking) 등의 다양한 방법을 사용하였다.  또한 에이전트(Agent)로 불리우는 SW 개발에 대한 관심이 커지고 있는데, 기존의 단방향 문서 찾기를 넘어서 다양한 툴의 활용, 그리고 양방향 또는 심지어 에이전트 간의 통신을 강화한 기능을 가지고 있다. 연구재단이 연구자를 위하여 에이전트를 제작할 경우 다양한 응용을 생각할 수 있다.  일예로, 신진 연구자에 대한 지원, 신규과제 공모 알리기, 관련 분야의 연구 동향 요약 등의 자료제공에 좀 더 적극적인 역할을할 수 있다.

def extract_ids_in_brackets(text):

faq_pattern = r'<FAQ ID: ([\d, ]+)>'

rule_match = re.search(rule_pattern, text)

faq_match = re.search(faq_pattern, text)

rule_ids = [int(id.strip()) for id in rule_match.group(1).split(',')] if rule_match else []

faq_ids = [int(id.strip()) for id in faq_match.group(1).split(',')] if faq_match else []

return rule_ids, faq_ids

def extract_ids_in_brackets(text):

if isinstance(text, list):

# Convert each dictionary to a string representation if necessary

text = ' '.join([str(item) if isinstance(item, dict) else item for item in text])

# Find content within '<>' and extract Rule ID and FAQ ID

rule_ids_in_brackets = re.findall(r'<Rule ID: ([\d, ]+)(?:, Rule ID: ([\d, ]+))*>', text) faq_ids_in_brackets = re.findall(r'<FAQ ID: ([\d, ]+)>', text)

# Flatten the rule IDs results, combining multiple instances

rule_ids = [id.strip() for group in rule_ids_in_brackets for id in group if id]

# Convert the results into lists of individual numbers

rule_ids = [id.strip() for ids in rule_ids for id in ids.split(',')]

faq_ids = [id.strip() for ids in faq_ids_in_brackets for id in ids.split(',')]

rule_ids_numbers = list(map(int, rule_ids))

faq_ids_numbers = list(map(int, faq_ids))

return rule_ids_numbers, faq_ids_numbers

rule_list = rule_string.replace('"', '').split(', ')

converted_rules = []

for rule in rule_list:

match = re.match(r'제(\d+)(?:조-?(\d+))?', rule)

if match:

if match.group(2):

converted_rules.append(f"{match.group(1)}.{match.group(2)}")

else:

converted_rules.append(match.group(1))

return converted_rules

def log_query(user_id, affiliation, query, response, top_rule_numbers, feedback=None, evaluation=None,file_path="query_log0620.csv"):

Logs the query details to a CSV file.

Parameters:

user_id (str): The ID of the user making the query.

affiliation (str): The affiliation of the user.

query (str): The query text.

response (str): The response to the query.

top_rule_numbers (list): A list of top rule numbers related to the query.

feedback (str, optional): Feedback provided by the user. Defaults to None.

evaluation (str, optional): Evaluation of the response. Defaults to None.

file_path (str, optional): The path to the CSV file. Defaults to "query_log0620.csv"."""
